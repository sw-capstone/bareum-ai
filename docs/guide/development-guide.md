# sw-capstone 개발 및 하네스 사용 가이드

이 문서는 `sw-capstone` 프로젝트를 처음 개발하는 사람이 브랜치 생성부터 코드 작성, 검사, 커밋, 푸시, PR, 리뷰와 병합까지 수행하는 전체 과정을 설명한다.

작업 순서와 명령만 빠르게 확인하려면 [팀원용 하네스 빠른 참고표](./team-quick-start.md)를 먼저 본다.

이 프로젝트는 다음 두 GitHub 저장소로 운영한다.

| 작업 내용                               | 저장소                      |
| --------------------------------------- | --------------------------- |
| 화면, 입력, 상태 표시, 공개 API 소비    | `sw-capstone/bareum-web`    |
| 백엔드 API, 작업 관리, AI, 계약, 하네스 | `sw-capstone/bareum-server` |

`bareum-web`은 서버의 공개 API 계약만 소비한다. 서버의 AI 처리 경계, DB, 프롬프트, 규칙 파일을 직접 참조하지 않는다.

## 1. 개발 흐름 한눈에 보기

```text
GitHub 이슈 확인
→ 작업 저장소 선택
→ 최신 develop 동기화
→ 이슈 단위 브랜치 생성
→ 기준 문서·계약·AGENTS.md 확인
→ 코드·문서·테스트 작성
→ 로컬 하네스·품질 검사
→ 커밋
→ 원격 푸시
→ PR 생성
→ GitHub Actions·하네스 검사
→ 리뷰 대응
→ 승인
→ 작업 브랜치를 develop에 Squash merge
→ 원격 작업 브랜치 삭제·로컬 동기화
```

`main`과 `develop`에는 직접 푸시하지 않는다. 모든 변경은 작업 브랜치와 PR을 통해 반영한다. 릴리스는 팀 전체가 검토하고 동의한 뒤 `develop`을 `main`에 Merge commit으로 병합한다.

## 2. 작업 시작 전 확인할 것

### 2.1 GitHub 이슈

코드 작성 전에 이슈 템플릿에서 작업 성격에 맞는 템플릿을 선택한다.

- 버그 수정: Bug
- 구조·성능 개선: Refactor
- 문서 작업: Docs
- 기능 추가: Feature
- 개발·실행 환경, 인프라, 빌드·배포, 의존성 정비: Chore

성능 개선은 우선 Refactor 템플릿과 `perf` 라벨로 관리한다. 성능 작업이 많아지거나 별도의 측정·검증 항목을 반복해서 관리하기 어려워질 때 Perf 템플릿 분리를 다시 검토한다.

선택한 템플릿의 필수 항목을 작성하고 담당자와 라벨을 설정한다. 현재 하네스는 이슈 본문의 내용을 검사하지 않는다.

기획 문서에 `결정 필요`, `팀 결정`, `멘토사 확인`, `검토`로 표시된 내용은 개발자가 임의로 확정하지 않는다.

### 2.2 기준 문서

프론트 작업은 다음 문서를 먼저 확인한다.

```text
bareum-web/AGENTS.md
bareum-web/README.md
bareum-web/docs/backend-integration.md
```

- `AGENTS.md`: 웹 저장소의 작업 경계와 검사 명령을 확인한다. AI 도구와 함께 작업할 때도 적용한다.
- `README.md`: 처음 환경을 준비하거나 실행·검사 명령을 찾을 때 본다.
- `docs/backend-integration.md`: 서버 API를 연결하거나 요청·응답·오류 형식을 변경할 때 확인한다. 일반적인 화면 수정마다 전체를 다시 읽을 필요는 없다.

서버 작업은 매번 아래 두 문서만 먼저 확인한다.

```text
bareum-server/AGENTS.md
bareum-server/README.md
```

그 다음 변경 범위에 직접 연결된 문서만 선택해서 확인한다.

| 작업 범위 | 추가로 확인할 문서 |
| --- | --- |
| 제품 기능·정책 변경 | Notion 기획 원문, `docs/product/service-spec.md` |
| 백엔드·AI 책임·실행 경계 변경 | `docs/architecture/repository-structure.md`, `docs/architecture/repository-boundaries.md`와 관련 결정 문서 |
| AI 규칙·프롬프트·평가 기준 변경 | 승인된 원천과 관련 결정 문서 |
| 웹과 서버의 책임·계약·경계 변경 | `docs/architecture/repository-structure.md`, `docs/architecture/repository-boundaries.md`와 관련 결정 문서 |
| 하네스 검사·정책·CI 변경 | `docs/harness/harness-v1.3.md`, `docs/harness/harness-file-roadmap.md` |
| 이슈·브랜치·PR·리뷰·병합 방식 변경 | `docs/guide/development-guide.md` |
| 공식 ID·제품 규칙 변경 | 해당하는 `docs/decisions/DEC-*.md`만 확인 |

`docs/architecture/`와 `docs/decisions/` 전체를 매번 읽지 않는다. 변경 파일과 직접 연결된 문서가 없으면 기본 문서만 확인하고 작업한다.

### 2.3 로컬 상태 확인

브랜치를 전환하거나 `pull`·`merge`를 실행하기 전에는 현재 브랜치의 로컬 변경을 확인한다. 변경사항을 확인하면 작업 중인 파일을 다른 브랜치에 잘못 섞거나 덮어쓰는 일을 줄일 수 있다.

```bash
git status --short
```

변경된 파일이 표시되면 작업 내용을 확인한 뒤 다음 작업을 진행한다. 기존 작업을 확인하지 않은 채 초기화하거나 덮어쓰지 않는다. 원격 변경을 반영하는 구체적인 명령은 작업 시작 전에는 4.1절, 작업 중인 브랜치에는 14절을 따른다. 작업 범위가 겹치는 경우에만 관련 GitHub 이슈·PR을 함께 확인한다.

## 3. 작업 저장소 선택

### 3.1 `bareum-web`에서 작업하는 경우

- 화면과 컴포넌트
- 사용자 입력
- 화면 상태
- 로딩·성공·실패 표시
- 공개 API 호출
- API 응답의 화면 변환
- 프론트 테스트

프론트는 다음 내부 구현에 직접 접근하지 않는다.

```text
서버 내부 프롬프트
DB
AI 모델 SDK
```

### 3.2 `bareum-server`에서 작업하는 경우

- 공개 API
- 인증·세션
- 파일 업로드
- 분석 작업 생성·조회·재시도
- 영속성
- AI 오케스트레이션
- 하네스와 저장소 문서
- 계약·규칙·프롬프트·평가 자산(확정 후)

서버 내부에서도 책임을 분리한다.

| 영역 | 담당 범위 |
| --- | --- |
| 백엔드 API 영역 | 세션, 업로드, 작업 상태, 영속성, 공개 API, AI 호출 조정 |
| AI 처리 영역 | 파싱, 규칙·검색·판정 등 AI 처리 책임 |
| `packages/contracts/` | 요청·응답·상태·오류 등 영역 간 형식(계약 확정 시 생성) |
| `harness/` | 현재 저장소·문서 정적 검사와 향후 계약·평가 검사 연결 |

이 표는 작업 책임을 설명한 것이지 현재 구현 경로를 의미하지 않는다. 백엔드·AI 코드, 제품 규칙, 기준 데이터·평가 자산의 실제 경로와 별도 프로세스·이미지 운영 여부는 관련 결정 후 생성한다. 현재는 이를 위한 임시 디렉터리를 만들지 않는다.

## 4. 브랜치 생성

### 4.1 최신 `develop` 받기

프론트 작업:

```bash
cd bareum-web
git switch develop
git pull --ff-only origin develop
```

서버 작업:

```bash
cd bareum-server
git switch develop
git pull --ff-only origin develop
```

### 4.2 작업 브랜치 생성

이슈 내용을 식별할 수 있는 작업 브랜치를 만든다.

```bash
git switch -c <작업-브랜치-이름>
```

작업 브랜치는 GitHub 이슈 하나에 하나만 만든다. 한 브랜치에 서로 관련 없는 여러 기능을 섞지 않는다.

## 5. 코드 작성 순서

### 5.1 단일 저장소 기능 변경

화면만 바뀌는 경우:

```text
기획 범위 확인
→ 기존 컴포넌트·Hook 확인
→ 코드 작성
→ 화면 상태별 테스트 작성
→ Mock API로 흐름 확인
→ 프론트 검사
```

서버 내부 기능만 바뀌는 경우:

```text
기획·아키텍처 확인
→ 담당 영역 결정
→ 코드 작성
→ 단위·통합 테스트 작성
→ 서버 하네스 검사
→ 서버 테스트
```

### 5.2 계약 변경

다음과 같은 변경은 계약 변경으로 처리한다.

- API 요청 필드 추가·삭제
- API 응답 필드 추가·삭제
- 상태값 변경
- 오류 코드 변경
- AI 결과 구조 변경
- 필드의 타입·필수 여부 변경
- 프론트와 서버 사이의 데이터 흐름 변경

공개 계약의 형식이 합의되면 다음 순서로 서버와 웹을 함께 변경한다.

```text
백엔드·AI 담당자와 필요한 소비자 간 형식 합의
→ 서버에 Schema·예시와 계약 테스트 작성
→ 하네스 검사 연결 및 서버 구현·검증
→ 웹 소비 코드와 소비자 테스트 갱신
→ 두 저장소의 PR을 연결해 검토
```

첫 계약이라면 이때 `packages/contracts/`를 생성한다. 아직 공개 계약이 확정되지 않았으므로 현재 폴더나 계약 검사가 이미 준비돼 있다고 가정하지 않는다. 계약을 서버와 프론트에서 각각 다르게 해석하지 않으며, 형식이 불명확하면 먼저 합의해 기록한다.

### 5.3 프론트 코드의 책임

프론트는 다음 흐름을 사용한다.

```text
화면
→ Hook
→ API 서비스
→ HTTP 클라이언트
→ 백엔드 공개 API
```

화면 컴포넌트에서 직접 `fetch`하지 않는다. 서버의 내부 AI 구현이나 DB를 직접 호출하지 않는다.

프론트가 확인해야 하는 화면 상태:

- 초기 상태
- 로딩
- 성공
- 부분 실패
- 전체 실패
- 판단보류
- 재시도
- 취소
- 권한 없음

### 5.4 구현 확정 후 적용할 서버·AI 검증 기준

백엔드·AI 실행 경계와 관련 기능이 확정된 뒤, 담당자는 다음 요구사항을 설계와 테스트에 반영한다.

- 계약에 맞는 입력·출력 생성
- 작업 상태 전이 검증
- 오류 코드 보존
- 원문 위치와 근거 보존
- 검증되지 않은 결과의 판단보류 처리
- 규칙·프롬프트·데이터·모델 버전 기록
- Trace와 Git SHA 기록

근거가 없거나 Schema 후검사를 통과하지 못한 결과를 확정 위반으로 노출하지 않는다. 이는 현재 자동으로 검사되는 항목의 목록이 아니라, 관련 기능이 구현될 때 영역 담당자가 테스트로 검증하고 하네스에 연결할 기준이다.

## 6. 개발 중 확인

작업 중 변경 범위를 확인할 필요가 있을 때 다음 명령을 실행한다.

```bash
git status --short
git diff
```

확인할 내용:

- 의도하지 않은 파일이 변경되지 않았는가?
- `.env`, 비밀번호, 토큰이 포함되지 않았는가?
- 빌드 결과물이 추가되지 않았는가?
- 이번 작업과 무관한 로컬 변경이 섞이지 않았는가?
- 계약 변경 시 예시와 테스트도 변경했는가?
- 문서 링크가 실제 파일을 가리키는가?
- 결정되지 않은 사항을 임의로 확정하지 않았는가?

## 7. 로컬 검사

### 7.1 서버 검사

```bash
cd bareum-server
./scripts/run-harness.sh check
./scripts/test-harness.sh
```

`run-harness.sh check`에 정의된 검사 항목과 현재 상태는 다음과 같다.

- **실행 중**: 현재 검사 대상이 있어 하네스가 실제로 실행하는 항목이다. 실행 결과는 통과 또는 실패로 따로 확인한다.
- **`not_applicable`**: 검사 코드는 있지만 현재 대상 파일이나 설정이 없어 이번에는 실행되지 않은 항목이다. 통과를 뜻하지 않는다.
- **향후 추가**: 검사 코드와 CI 연결이 아직 없는 항목이다. 리포트의 검사 상태가 아니며, 관련 구현·자산과 테스트가 준비되면 추가한다.

- 정책 사전 검증 — 항상 실행
  - `harness/policy.json`의 버전과 검사 설정 형식이 올바른지 확인한다. 정책을 읽지 못하면 나머지 검사를 실행하지 않고 실패 처리한다.
- 필수 경로 — 실행 중
  - `harness/policy.json`에 필수로 등록된 파일이 실제로 존재하는지 확인한다. 파일 내용이나 기능 동작까지 검증하지는 않는다.
- JSON 형식 — 실행 중
  - 저장소의 JSON 파일이 문법 오류 없이 읽히는지 확인한다. 값이 제품 요구사항에 맞는지는 별개다.
- Schema 헤더 — `not_applicable`
  - `*.schema.json` 파일에 `$schema`, `$id`, `type` 항목이 있는지 확인하는 코드가 있다. 현재 대상 Schema 파일이 없어 실행되지 않는다.
- Schema 예시 — `not_applicable`
  - 정책에 등록된 예시 JSON이 해당 Schema를 만족하는지 확인하는 코드가 있다. 현재 등록된 Schema·예시 쌍이 없어 실행되지 않는다.
- ID 등록·중복·참조 — `not_applicable`
  - ID 레지스트리의 형식, 중복과 참조 오류를 확인하는 코드가 있다. 현재 레지스트리 파일이 없어 실행되지 않는다.
- Markdown 링크 — 실행 중
  - 문서의 로컬 파일 링크가 깨지지 않았는지 확인한다.
- 비밀정보 패턴 — 실행 중
  - 파일에 토큰·비밀번호 등으로 보이는 문자열이 있는지 패턴으로 확인한다. 모든 비밀정보를 완벽하게 탐지한다는 의미는 아니다.
- 제품 구현 요약 문서 기준 — 실행 중
  - `docs/product/service-spec.md`에 정책이 요구하는 구성이 있는지 확인한다. 문서 내용의 정확성은 판정하지 않는다.
백엔드·AI 동작, 계약 호환성, 근거·상태 보존 등 안전 불변식, 평가 데이터·성능 회귀 검사는 관련 구현과 자산이 준비된 뒤 추가한다. 현재 확정되지 않은 백엔드·AI 경로를 대상으로 하는 검사는 없다.

`test-harness.sh`는 현재 하네스 검사기의 자체 회귀 테스트를 실행한다. AI 처리 코드(`src/bareum_ai/`) 테스트 명령과 CI 연결은 첫 테스트가 추가될 때 함께 정한다.

### 7.2 웹 검사

`bareum-web`에서 처음 환경을 준비할 때는 `npm ci`로 의존성을 설치한다. 이후 변경을 검사할 때는 다음 명령을 실행한다.

```bash
cd bareum-web
npm run check
```

현재 공개 계약이 확정되지 않아 계약 스냅샷 검사는 실행하지 않는다. 계약이 추가되면 서버 계약 변경과 웹 소비 코드·검사를 함께 검토한다.

`npm run check`는 다음을 실행한다.

```text
Prettier
ESLint
Vitest
TypeScript
Vite production build
```

Mock API 성공은 실제 서버 연동 성공을 의미하지 않는다. 실제 연동에서는 요청 형식, 분석 ID, 상태 폴링, 결과 Schema, 오류 코드, 취소, 파일 다운로드를 별도로 확인한다.

## 8. 하네스 검사 결과 해석

| 리포트 상태 | 의미 | 개발자가 할 일 |
| --- | --- | --- |
| `passed` | 대상이 있는 검사를 실제 실행해 통과함 | PR에 실행 결과 기록 |
| `failed` | 검사가 실행되어 실패함 | 파일·ID·원인을 수정하고 재실행 |
| `not_applicable` | 검사 코드는 있지만 대상 파일이나 설정이 없어 실행되지 않음 | 통과로 기록하지 않고 대상이 추가되면 다시 확인 |
| `disabled` | 정책에서 검사가 비활성화됨 | 비활성 사유와 영향을 검토 |

`미연결`은 검사 코드와 CI 연결이 아직 없는 향후 작업을 가리키는 문서 표현이고, `판단보류`는 근거가 부족한 제품 결과의 상태다. 둘 다 현재 하네스 리포트의 검사 상태값은 아니다.

주요 서버 하네스 ID:

```text
HAR-STRUCT-001   필수 경로
HAR-POLICY-001   하네스 정책
HAR-JSON-001     JSON
HAR-SCHEMA-001  Schema
HAR-ID-*         ID
HAR-DOC-*        문서 링크
HAR-SEC-001      비밀정보
HAR-PRODUCT-001  제품 구현 요약 문서
```

검사 실패를 숨기거나 검사 파일을 제외하지 않는다. 리포트 파일을 삭제해서 통과시키지 않는다.

## 9. 커밋

검사 전에 변경사항을 확인한다.

```bash
git status --short
git diff
```

필요한 파일만 스테이징한다.

```bash
git add src/features/upload/UploadPage.tsx
git add src/hooks/useDocumentUpload.ts
git add src/hooks/useDocumentUpload.test.ts
git diff --staged
```

변경 목적을 알아볼 수 있는 커밋 메시지를 `태그: 커밋 본문` 형식으로 작성한다. 이슈·PR 제목의 `[Chore]` 형식과 커밋 메시지 형식은 별개다.

```bash
git commit -m "feat: 문서 업로드 입력 검증 추가"
```

한 커밋에는 하나의 논리적 변경만 담는다. `수정`, `완료`, `update`처럼 목적이 드러나지 않는 메시지는 피한다. 예시는 `feat: 기능 추가`, `fix: 오류 수정`, `docs: 문서 수정`, `chore: 환경·구조 정리`와 같다.


그 이후에는:

```bash

```

공유한 브랜치를 강제로 덮어쓰지 않는다.

## 11. PR 생성

일반 작업 PR은 `develop`을 대상으로 한다. `main` 대상 PR은 팀이 릴리스를 검토하고 동의한 경우에만 만든다. PR 제목은 변경 목적이 분명하게 드러나도록 작성하고, 제목과 대상 브랜치를 반드시 확인한다.

PR 본문은 PR 템플릿을 사용한다.

```markdown
## 🔗 관련 이슈

## 📝 변경 내용

## ✅ 테스트 및 검증

## 💬 리뷰 참고사항

## ☑️ 확인사항
```

필요한 하네스 정보는 기존 PR 항목에 기록한다.

- `변경 내용`: 변경 영역, 계약 영향과 관련 공식 ID
- `테스트 및 검증`: 실행한 하네스 명령과 테스트 결과, 미실행 검사와 사유
- `리뷰 참고사항`: 호환성·개인정보·권한 영향, 남은 위험과 재검토 조건

위 하네스 관련 세부 내용이 없으면 생략할 수 있다. 누락이 아니라 검토 후 해당하지 않는다는 점을 명확히 할 필요가 있을 때만 `해당 없음: <간단한 이유>`를 선택적으로 작성한다. 현재 하네스는 PR 본문을 자동 검사하지 않으므로 이 기록은 리뷰와 변경 추적을 위한 사람용 근거다.

PR 작성자가 필요한 리뷰어를 직접 지정한다.

## 12. GitHub Actions와 리뷰

PR을 올리면 GitHub Actions가 실행된다.

서버:

```text
Harness / check
├── ./scripts/run-harness.sh check
└── ./scripts/test-harness.sh
```

웹:

```text
Harness / check
└── npm run check
```

### 12.1 현재 자동으로 확인하는 범위

서버의 검사 항목과 상태는 [7.1 서버 검사](#71-서버-검사)에 정리했다. CI는 해당 정적 검사와 하네스 자체 테스트를 실행한다.

웹 CI는 `npm run check`를 통해 포맷, ESLint, 단위 테스트, TypeScript 검사와 프로덕션 빌드를 실행한다.

Schema 헤더, Schema·예시 쌍과 ID 레지스트리 검사는 코드가 있지만 현재 대상이 없어 `not_applicable`이다. 이는 통과가 아니다. 백엔드·AI 코드 검사와 계약·평가 검사는 실제 구현, 자산과 실행 명령이 준비된 뒤 연결한다.

하네스는 다음을 하지 않는다.

- 프론트·백엔드 코드를 대신 작성하지 않음
- 실패한 코드를 자동 수정하지 않음
- 리뷰어를 자동 지정하지 않음
- API 설계 결정을 대신 내리지 않음
- UI 사용성을 판단하지 않음
- AI 결과가 실제로 정확한지 자동 확정하지 않음
- 결정 대기 사항을 임의로 확정하지 않음

### 12.2 향후 확장되는 범위

프로젝트 구현이 진행되면 하네스는 작업 내용과 준비된 자산에 맞춰 다음 검사를 선택적으로 추가한다.

| 추가되는 대상 | 하네스에 추가되는 검사 | 팀원이 해야 하는 일 |
| --- | --- | --- |
| API·AI 처리·학습 코드 | 영역별 포맷·린트·타입·단위·통합·빌드 검사 | 해당 영역 담당자가 실행 가능한 코드·검사와 테스트 명령 제공 |
| 요청·응답·상태·오류 계약 | Schema·예시 검증, 이전 버전 호환성 검사 | 해당 계약 담당자가 계약과 형식·호환성·회귀 검사를 작성하고 웹 소비 영향 확인 |
| 규칙·프롬프트·기준 데이터 | ID·버전·해시·출처·기준일·체크섬 검사 | 변경 이유와 사용한 자산 버전 기록 |
| 파싱·검색·판정·수정안 구현 | 원문 위치, 근거 게이트, 실패 상태와 CBR 안전 불변식 검사 | 정상·실패 사례와 기대 결과 제공 |
| 검수된 평가셋과 H0 | 데이터 누수, 지표 계산과 성능 회귀 검사 | 동일 조건의 평가 설정과 검수 이력 제공 |
| 서버 계약의 웹 동기화 | 계약 버전·Git SHA·웹 소비자 호환성 검사 | 프론트 소비 코드는 사람이 수정하고 검사 결과 확인 |
| 실제 배포·외부 API·사용자 문서 | 리포트 Schema, 로그 마스킹, 재시도·복구 검사 | 보존·삭제·권한·장애 대응 기준 제공 |

확장되더라도 하네스가 기능 코드를 대신 작성하거나 자동 수정하는 것은 아니다. 각 영역 담당자는 실제 코드·계약·테스트와 형식·호환성·회귀 검사를 작성하고, 하네스 담당자는 공통 기준을 리뷰한 뒤 반복 실행 가능한 검사·리포트·CI로 연결한다.

작업별 시작 조건, 추가할 파일과 완료 조건은 [`harness-file-roadmap.md`](../harness/harness-file-roadmap.md)를 따른다.

## 14. 기준 브랜치 변경 반영

PR이 오래 열려 `develop`에 새 변경이 들어왔거나 충돌이 발생하면 작업 브랜치에서 기준 브랜치를 반영한다.

```bash
git fetch origin
git merge origin/develop
```

충돌 해결 후 검사한다.

```bash
# 서버
./scripts/run-harness.sh check
./scripts/test-harness.sh

# 웹
npm run check
```

아직 원격에 푸시하지 않은 개인 로컬 작업 브랜치에서는 커밋 이력을 정리하기 위해 rebase를 사용할 수 있다. 원격에 공유한 뒤에는 리뷰 이력이 바뀌지 않도록 rebase하거나 강제 푸시하지 않고, 위와 같이 기준 브랜치를 `merge`한다.

## 15. 승인과 병합

병합 전 조건:

- PR 목적과 범위가 명확함
- 관련 이슈 연결
- 필수 검사 통과
- 최소 1명 승인
- 해결되지 않은 리뷰 대화 없음
- 계약·하네스·평가 변경 시 관련 담당자 검토
- 최신 기준 브랜치 반영

작업 브랜치를 `develop`에 병합할 때는 Squash merge를 사용한다. 새 리뷰 대상 커밋이 추가되면 변경 내용을 다시 리뷰받는다. Auto-merge와 관리자 우회는 사용하지 않는다.

`develop`에서 `main`으로 릴리스할 때는 팀 전체가 검토하고 동의한 뒤 Merge commit을 사용한다. 일반 작업 브랜치를 `main`에 직접 병합하지 않는다.

병합 후 로컬을 정리한다.

```bash
git switch develop
git pull --ff-only origin develop
git branch -d <작업-브랜치-이름>
```

## 16. 계약 변경의 전체 예시

### 16.1 서버 계약 PR

```bash
cd bareum-server
git switch develop
git pull --ff-only origin develop
git switch -c <서버-계약-작업-브랜치>
```

계약이 처음 추가되는 경우의 작업 예시:

```text
packages/contracts/ 생성 및 Schema·예시 작성
→ 계약 테스트 작성
→ 서버 구현과 하네스 검사 연결
→ 서버 하네스·테스트 실행
→ 서버 PR 생성
```

```bash
./scripts/run-harness.sh check
./scripts/test-harness.sh
```

검사가 통과하면 9~10절에 따라 이번 작업의 파일만 스테이징하고 커밋·푸시한다.

### 16.2 웹 소비자 PR

서버 계약 변경을 확인한 뒤 웹에서 작업한다.

```bash
cd bareum-web
git switch develop
git pull --ff-only origin develop
git switch -c <웹-계약-작업-브랜치>
```

확인할 것:

- 기존 프론트 Schema 영향
- 상태별 화면 표시
- Mock 응답과 테스트

```bash
npm run check
```

검사가 통과하면 이번 작업의 파일만 스테이징하고 커밋·푸시한다.

서버 PR과 웹 PR은 서로 연결한다. 서버 계약이 확정되지 않았는데 웹이 임의의 계약을 먼저 확정하지 않는다.

## 17. 사람과 하네스의 역할

백엔드·AI·프론트 담당자는 각자 맡은 기능과 계약 자산을 구현하고, 해당 영역의 형식·호환성·회귀 테스트를 작성한다. 검사 실패가 작업 내용에서 비롯됐다면 해당 작성자가 수정한다. PR에는 실행 결과를 남기고 관련 리뷰어를 지정하며, 영역별 검사를 추가·변경했다면 하네스 담당자도 리뷰어로 지정한다.

하네스 담당자는 영역별 검사 기준을 리뷰하고 공통 실행 명령·정책·CI에 연결한다. 현재 서버 하네스는 저장소와 문서의 정적 검사 및 자체 테스트를 실행한다. 계약 호환성, 백엔드·AI 동작과 평가 회귀 검사는 관련 구현·자산·테스트가 준비된 뒤 추가한다.

자동 검사는 반복 가능한 기준을 확인할 뿐, 기능 코드를 작성하거나 수정하지 않고 설계·제품 품질에 대한 사람의 리뷰를 대신하지 않는다.

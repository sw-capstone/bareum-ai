# AI 저장소 개발 가이드

## 1. 작업 전 확인

AI 작업은 다음 문서부터 확인한다.

```text
README.md
AGENTS.md
```

하네스 변경은 `docs/harness/harness-v1.4.md`와 `docs/harness/harness-file-roadmap.md`를 추가로 확인한다. 서버↔AI 형식에 영향을 주는 변경은 서버의 계약과 관련 PR을 함께 확인한다.

## 2. 브랜치 준비

팀 협업 규칙에 따라 이슈를 생성하고 `develop`에서 작업 브랜치를 만든다.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c <작업-브랜치>
```

브랜치를 전환하거나 원격 변경을 반영하기 전에는 필요한 경우 `git status --short`로 현재 작업이 남아 있는지 확인한다.

AI 실행 코드 작업에는 uv가 필요하다. 처음 작업하거나 의존성이 바뀌었으면 `uv sync`로 환경을 맞춘다.

## 3. 현재 검사

로컬 검사는 Push 전 사전 확인이나 CI 실패 재현이 필요할 때 실행한다.

```bash
./scripts/run-harness.sh check
./scripts/test-harness.sh
```

첫 명령은 저장소 구조와 문서를 검사하고, 두 번째 명령은 검사기 자체 테스트를 실행한다. CI도 같은 진입점을 사용한다.

현재 검사 범위는 다음과 같다.

| 검사 | ID | 내용 |
| --- | --- | --- |
| 필수 경로 | `HAR-STRUCT-001` | 정책에 등록한 파일이 존재하는지 확인 |
| JSON 문법 | `HAR-JSON-001` | JSON 파일을 파싱할 수 있는지 확인 |
| Markdown 링크 | `HAR-DOC-001`~`002` | 저장소 내부 링크가 유효한지 확인 |
| 비밀정보 의심 패턴 | `HAR-SEC-001` | 토큰·비밀키로 보이는 문자열이 포함됐는지 확인 |

현재 검사는 AI 결과의 정확성·성능, 계약 호환성이나 서버 연동을 판정하지 않는다.

## 4. AI 구현과 검사 추가

AI 기능을 구현할 때 영역 담당자는 기능 코드(`src/bareum_ai/`)와 테스트를 작성하고 실행 명령을 CI에 연결한다. AI 코드 테스트 명령과 CI 연결은 첫 테스트가 추가될 때 함께 정한다. 모델·프롬프트·규칙·평가 데이터를 추가할 때는 다음 항목을 함께 정한다.

- 입력과 기대 결과
- 통과·실패 기준
- 사용한 모델·프롬프트·데이터 버전
- 정상·경계·실패 사례
- 결과 재현에 필요한 Git SHA와 설정

새 하네스 검사는 영역 담당자가 작성하고 하네스 담당자를 필수 리뷰어로 지정한다. 기준이 없는 자산이나 검사를 먼저 만들지 않는다.

## 5. 계약과 연동 변경

서버↔AI 계약은 `bareum-server/packages/contracts/`에서 관리한다. 형식을 바꾸는 경우 서버와 AI의 제공자·소비자 구현 및 테스트를 함께 검토하고 관련 PR을 서로 연결한다.

실제 실행 환경이 준비되면 다음 순서로 검사를 확장한다.

1. 계약 형식과 호환성 검사
2. 핵심 성공 흐름
3. 시간 초과·오류 전달
4. 평가 데이터 기반 성능 회귀

## 6. Pull Request

PR에는 변경 목적, 관련 이슈·계약, 실행한 검사와 남은 위험을 기록한다. CI 결과와 리뷰를 확인한 뒤 팀의 병합 규칙에 따라 처리한다.

검사 코드·정책·CI를 변경했다면 하네스 담당자를 필수 리뷰어로 지정한다.

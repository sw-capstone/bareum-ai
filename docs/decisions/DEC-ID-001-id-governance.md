# DEC-ID-001 ID 운영 규칙

- 상태: 결정
- 결정일: 2026-09-08
- 소유 역할: `harness-maintainers`
- 기준 파일(생성 예정): `packages/contracts/id-registry.json`

## 목적

GitHub 이슈 번호는 작업을 추적하고, 프로젝트 ID는 여러 파일과 버전에 걸쳐 유지되는 공식 자산을 추적한다. 두 번호를 PR에서 연결해 작업 과정과 장기 자산을 함께 찾을 수 있게 한다.

## ID 형식

```text
<TYPE>-<DOMAIN>-<NNN>
```

- 모두 대문자로 작성한다.
- 번호는 유형과 도메인 조합별로 `001`부터 증가한다.
- 발급된 ID는 삭제하거나 다른 의미로 재사용하지 않는다.

### 유형

| TYPE | 대상 | 예시 |
|---|---|---|
| `FEAT` | 사용자 기능·제품 흐름 | `FEAT-DOC-001` |
| `API` | 영역 간 API·이벤트 계약 | `API-DOC-001` |
| `RULE` | 제품 판정 규칙 | `RULE-REG-001` |
| `DATA` | 기준 데이터·스냅샷 | `DATA-LAW-001` |
| `EVAL` | 평가셋·평가 설정·기준 결과 | `EVAL-REG-001` |
| `TEST` | 핵심 통합·불변식 테스트 | `TEST-FLOW-001` |
| `HAR` | 하네스 검사·정책 | `HAR-CI-001` |
| `DEC` | 아키텍처·운영 결정 | `DEC-REPO-001` |

### 도메인

초기 도메인은 `DOC`, `AUTH`, `WEB`, `SERVER`, `AI`, `REG`, `LAW`, `FLOW`, `CI`, `REPO`, `ID`, `COMMON`, `STRUCT`, `JSON`, `SCHEMA`, `SEC`를 사용한다. 새 도메인이 필요하면 기존 의미와 겹치지 않는지 확인한 뒤 이 문서와 레지스트리를 같은 PR에서 갱신한다.

## 발급 대상

다음 조건 중 하나에 해당하는 자산에만 ID를 발급한다.

- 둘 이상의 영역이나 담당자가 참조한다.
- 독립적인 수용 기준이나 품질 기준이 있다.
- 버전이 바뀌어도 추적해야 한다.
- 실패 시 회귀 테스트나 평가 결과와 연결해야 한다.

함수, 일반 문서, 임시 메모, 사소한 리팩터링과 모든 커밋에는 ID를 발급하지 않는다.

## 발급 절차

1. 팀원이 GitHub 이슈에 신규 ID 필요 여부와 제안 유형·도메인을 작성한다.
2. `harness-maintainers`가 발급 대상인지 확인한다.
3. 같은 유형·도메인의 마지막 번호 다음 번호를 선택한다.
4. 담당자가 확정한 ID 레지스트리에 ID, 상태, 소유 역할과 설명을 추가한다.
5. 하네스 검사를 실행하고 ID 등록 PR을 병합한다.
6. 기능 PR에서 이슈 번호와 발급된 ID를 함께 연결한다.

주 담당자와 보조 담당자 모두 발급할 수 있지만, 같은 번호 충돌을 막기 위해 ID 등록 PR이 병합된 뒤 해당 ID를 사용한다.

## 상태와 소유자

- `draft`: 제안 또는 구현 중
- `active`: 승인돼 사용 중
- `deprecated`: 더 이상 사용하지 않지만 추적을 위해 보존
- `owner`: 개인 이름이 아니라 `harness-maintainers`, `ai-team` 같은 역할명을 기록

기존 ID의 의미를 바꿔야 하면 해당 ID를 `deprecated`로 바꾸고 새 ID를 발급한다. 대체 ID가 있으면 `replaced_by`로 연결한다.

## GitHub에서 표시하는 위치

- 브랜치: GitHub 이슈 번호 사용
- 이슈: 관련 ID 또는 신규 ID 요청 표시
- PR 제목: 변경 목적이 드러나도록 작성하고 병합 전에 확인
- PR 본문: `Closes #42`와 관련 공식 ID 기록
- 계약·규칙·평가 파일: 해당 항목의 ID 필드 사용
- 테스트: `verified_by` 또는 테스트 메타데이터로 연결

## 재검토 조건

- 수동 발급 충돌이 반복되는 경우
- ID 수가 늘어 자동 발급 도구가 필요한 경우
- 멀티레포 전환으로 중앙 레지스트리 배포 방식이 달라지는 경우

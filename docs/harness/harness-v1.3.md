## 1. 하네스의 역할

하네스는 저장소의 변경이 정해진 구조와 품질 기준을 지키는지 자동으로 확인하는 검사 체계다.

하네스가 하는 일은 다음과 같다.

- 필수 파일과 디렉터리의 존재 여부 확인
- JSON 형식과 정책 파일의 유효성 확인
- Markdown 내부 링크의 유효성 확인
- 저장소에 비밀정보로 보이는 값이 포함되었는지 확인
- 서버 레포에서 관리하는 구현 요약 문서의 필수 표식 확인
- 검사 결과를 CI와 JSON 리포트로 제공

하네스는 코드를 대신 작성하거나 수정하지 않는다. 검사에서 실패하면 실패 위치와 이유를 제공하고, 변경 수정과 재검사는 개발자가 수행한다.

## 2. 현재 하네스 구조

하네스와 직접 관련된 현재 경로는 다음과 같다.

```text
bareum-server/
├── .github/
│   └── workflows/
│       └── harness.yml       # GitHub Actions 실행 정의
├── docs/
│   └── harness/
│       ├── harness-v1.3.md   # 현재 구조 설계 문서
│       └── harness-file-roadmap.md
├── harness/
│   ├── policy.json            # 필수 경로와 검사 활성화 정책
│   ├── requirements.txt       # 실행 의존성
│   ├── src/project_harness/   # 검사기와 CLI
│   ├── tests/                 # 하네스 자체 테스트
│   ├── README.md              # 하네스 사용 안내
│   ├── AGENTS.md              # 하네스 구현 지침
│   └── reports/               # 실행 리포트 저장 위치
│       ├── .gitkeep           # 디렉터리 유지용 파일
│       └── report.json        # 실행 시 생성되며 Git에는 저장하지 않음
└── scripts/
    ├── run-harness.sh         # 로컬·CI 검사 진입점
    └── test-harness.sh        # 하네스 자체 테스트 진입점
```

각 경로의 역할은 다음과 같다.

| 경로 | 역할 |
| --- | --- |
| `.github/workflows/harness.yml` | Push와 Pull Request에서 검사와 자체 테스트 실행 |
| `harness/policy.json` | 필수 경로, 검사 종류, 정책 버전 관리 |
| `harness/src/project_harness/` | 검사 로직과 명령행 실행기 관리 |
| `harness/tests/` | 검사기의 입력·판정·상태 구분 검증 |
| `harness/reports/` | 실행 시 생성되는 JSON 결과 저장 위치 |
| `scripts/` | 로컬과 CI가 같은 명령을 사용하도록 실행 방식 통일 |
| `docs/harness/` | 하네스 구조와 향후 확장 방향 문서화 |

`harness/reports/report.json`은 실행 중 생성되는 결과 파일이며, 하네스 구현 코드나 기준 문서가 아니다.

## 3. 검사 실행 흐름

```text
개발자가 브랜치에서 변경
        ↓
로컬 하네스 검사 실행
        ↓
검사 결과와 JSON 리포트 확인
        ↓
Pull Request 생성
        ↓
GitHub Actions에서 동일한 검사와 자체 테스트 실행
        ↓
실패 시 개발자가 수정 후 재실행
```

로컬에서 다음 명령을 사용한다.

```bash
./scripts/run-harness.sh check
./scripts/test-harness.sh
```

첫 번째 명령은 저장소 검사를 실행하고, 두 번째 명령은 하네스 검사기 자체의 테스트를 실행한다. CI도 같은 두 진입점을 사용하므로 로컬과 Pull Request의 검사 기준이 달라지지 않는다.

## 4. 현재 검사 항목

현재 정책 버전은 `1.3.0`이다.

| 검사 | 검사 ID | 상태 | 역할 |
| --- | --- | --- | --- |
| 정책 사전 검증 | `HAR-POLICY-001` | 항상 실행 | 정책의 버전과 검사 설정 형식 확인 |
| `required_paths` | `HAR-STRUCT-001` | 실행 중 | 정책에 등록된 필수 경로가 존재하는지 확인 |
| `json_syntax` | `HAR-JSON-001` | 실행 중 | 저장소의 JSON 파일이 올바른 형식인지 확인 |
| `schema_headers` | `HAR-SCHEMA-001` | 해당 없음 | Schema 파일이 추가되면 필수 헤더를 확인 |
| `schema_examples` | `HAR-SCHEMA-002` | 해당 없음 | Schema 예시가 정책에 등록되면 예시를 확인 |
| `id_registry` | `HAR-ID-001`~`HAR-ID-005` | 해당 없음 | ID 레지스트리가 추가되면 형식·중복·참조를 확인 |
| `markdown_links` | `HAR-DOC-001`~`HAR-DOC-002` | 실행 중 | Markdown의 저장소 내부 링크가 실제 파일을 가리키는지 확인 |
| `secret_patterns` | `HAR-SEC-001` | 실행 중 | 비밀정보로 보이는 패턴이 포함되었는지 확인 |
| `product_spec` | `HAR-PRODUCT-001` | 실행 중 | 서버 구현 요약 문서에 필요한 표식이 있는지 확인 |

`실행 중`은 현재 대상에 대해 검사를 수행한다는 의미다. `해당 없음`은 검사 코드가 없다는 뜻이 아니라, 현재 저장소에 검사 대상 자산이 없어 실행할 수 없다는 의미다. 대상 자산이 실제로 추가되고 기준이 확정되면 정책과 테스트를 함께 갱신한다.

## 5. 검사 결과와 실패 처리

검사 결과는 다음 상태로 구분한다.

| 상태 | 의미 |
| --- | --- |
| `passed` | 검사 조건을 통과함 |
| `failed` | 검사 조건을 위반함 |
| `not_applicable` | 현재 검사 대상이 없어 적용하지 않음 |
| `disabled` | 정책에서 검사를 비활성화함 |

실패 결과에는 검사 ID, 대상 경로, 실패 이유가 포함된다. 결과는 `harness/reports/report.json`에 기록되며, CI에서는 해당 리포트를 아티팩트로 보존한다.

하네스는 자동 수정 기능을 사용하지 않는다. 자동 수정이 필요한 경우에도 의미 변경이 발생할 수 있으므로, 별도 정책과 테스트를 먼저 확정해야 한다.

## 6. 검사 ID와 변경 추적

하네스 검사는 `HAR-*` 형식의 고유 ID로 식별한다. 각 검사는 다음 정보를 가져야 한다.

- 검사 ID
- 검사 대상
- 판정 조건
- 실패 메시지
- 자체 테스트

검사 정책을 변경할 때는 `harness/policy.json`, 검사 코드, 자체 테스트, 관련 문서를 함께 확인한다. 검사 결과에 영향을 주는 변경은 Pull Request에서 변경 이유와 검증 결과를 남긴다.

## 7. CI와 Pull Request에서의 역할

GitHub Actions는 하네스 검사를 자동 실행하는 실행 환경이다. GitHub Actions 자체가 하네스의 기준이나 검사 로직은 아니며, 하네스의 실행을 담당한다.

현재 CI는 다음을 수행한다.

1. 저장소를 checkout한다.
2. Python 실행 환경과 의존성을 준비한다.
3. `./scripts/run-harness.sh check`를 실행한다.
4. `./scripts/test-harness.sh`를 실행한다.
5. 검사 리포트를 아티팩트로 업로드한다.

검사 실패 시 개발자가 실패 원인을 확인하고 코드를 수정한 뒤 다시 Push한다. 하네스 담당자는 검사 기준과 검사 코드의 변경을 리뷰하며, 하네스가 애플리케이션 코드를 대신 수정하지 않는다.

## 8. 향후 확장 원칙

새로운 검사 대상이 확정되면 다음 순서로 하네스에 연결한다.

1. 검사 대상과 통과 기준을 문서로 확정한다.
2. `HAR-*` 검사 ID와 실패 조건을 정의한다.
3. 검사 코드를 추가한다.
4. 통과·실패·해당 없음 사례를 자체 테스트로 추가한다.
5. `policy.json`과 CI 연결을 갱신한다.
6. 로컬 검사와 CI에서 동일하게 동작하는지 확인한다.

계약, Schema, ID 레지스트리, 제품 AI 평가와 같은 자산은 실제 형식과 기준이 확정된 뒤 각각의 검사로 추가한다. 기준이 확정되지 않은 자산이나 디렉터리를 하네스 문서만으로 미리 생성하지 않는다.

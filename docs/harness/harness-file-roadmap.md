# 하네스 후속 파일 추가 로드맵

문서 상태: 작업별 하네스 확장 기준
적용 문서: `harness-v1.3`
목적: 실제 작업과 검증 자산이 준비된 경우에만 필요한 하네스 파일과 검사를 추가한다.

이 문서는 순서대로 모두 적용하는 단계표가 아니다. 작업 내용에 해당하는 항목만 선택적으로 적용한다. 아래에 나오는 미래 경로는 현재 저장소 구조가 아니라, 관련 결정과 구현이 완료된 뒤 검토할 예시다.

## 1. 공통 원칙

1. 실제 검사 대상과 통과 기준이 생긴 뒤 검사 파일을 추가한다.
2. 각 담당자는 본인 영역의 형식·호환성·회귀 검사를 작성하고, 하네스 담당자는 공통 정책·CI·실행 연결을 리뷰한다.
3. 새 검사는 `HAR-*` ID, 입력, 판정 조건, 실패 메시지와 실패 재현 테스트를 함께 갖는다.
4. 경로·정책·실행 명령이 바뀌면 검사 코드, 자체 테스트, CI와 관련 문서를 함께 갱신한다.
5. 실행하지 않은 검사를 통과로 기록하지 않는다. 대상이 없으면 `not_applicable`, 정책상 끄면 `disabled`로 기록한다.
6. 확정되지 않은 백엔드·AI·인프라 경로와 빈 프로젝트 자산을 미리 만들지 않는다.
7. 하네스는 제품 코드를 자동 수정하지 않는다.
8. 현재는 `CODEOWNERS`를 사용하지 않고, PR 작성자가 관련 담당자와 하네스 담당자를 리뷰어로 지정한다.
9. 이슈·PR 템플릿은 확정된 협업 규칙을 기준으로 사용하고, 하네스 추적 정보는 기존 PR 항목의 작성 안내에 포함한다.
10. 현재 하네스는 이슈·PR 본문을 자동 해석하지 않고, 템플릿 파일의 존재와 저장소 정적 품질을 확인한다.

## 2. 현재 존재하는 하네스 파일

| 경로 | 역할 |
| --- | --- |
| `harness/policy.json` | 필수 경로, 활성 검사와 문서 표식 설정 |
| `harness/src/project_harness/checks.py` | 저장소·JSON·Schema·ID·문서·비밀정보 검사 |
| `harness/src/project_harness/schema.py` | JSON Schema 검증 |
| `harness/src/project_harness/cli.py` | 검사 실행과 JSON 리포트 생성 |
| `harness/tests/test_checks.py` | 하네스 검사기 자체 회귀 테스트 |
| `scripts/run-harness.sh` | 로컬·CI 공통 검사 진입점 |
| `scripts/test-harness.sh` | 하네스 자체 테스트 진입점 |
| `.github/workflows/harness.yml` | Push·Pull Request 자동 실행 |
| `docs/harness/harness-v1.3.md` | 현재 하네스 구조와 검사 범위 |

## 3. 작업별 적용 기준

### 3.1 일반 저장소·문서 변경

적용 조건:

- 코드, 문서, 설정 또는 GitHub 운영 파일을 변경하는 작업

하네스 담당자가 확인할 내용:

- 필수 경로가 유지되는지
- JSON 문법과 Markdown 내부 링크가 유효한지
- 비밀정보로 보이는 값이 없는지
- 관련 문서 표식과 정책 경로가 유지되는지

완료 조건:

- `./scripts/run-harness.sh check` 통과
- 변경 내용과 검증 결과를 PR에 기록

### 3.2 실행 코드가 추가된 작업

적용 조건:

- 실제 실행 코드와 재현 가능한 로컬 명령이 추가됨
- 실행 경로와 담당 범위가 팀에서 확정됨

추가 검토 내용:

- 담당자가 포맷·린트·타입·단위·통합 검사를 제공
- 하네스 담당자가 `scripts/check-<area>.sh` 형태의 공통 진입점과 CI 연결을 검토
- 로컬과 CI가 동일한 명령을 사용하는지 확인

실행 경로와 프로젝트 설정은 확정된 구조에 맞춰 추가한다. 확정 전에는 `apps/`, `rules/`, `data/`, `evals/` 등의 빈 스캐폴드를 만들지 않는다.

### 3.3 계약이 확정된 작업

적용 조건:

- 서버와 웹 또는 서버 내부 영역 사이의 요청·응답·상태·오류 형식이 합의됨
- Schema와 유효·무효 예시가 준비됨

추가 검토 내용:

- Schema 헤더와 예시 검증
- 필수 필드·enum·오류 형식 검증
- 제공자·소비자 호환성 검증
- 계약 버전과 Git SHA 추적
- 웹 소비자 검증이 서버 계약 변경과 함께 실행되는지 확인

계약의 실제 위치와 파일명은 관련 결정 후 확정한다. 계약이 확정되기 전에는 `packages/contracts/`를 생성하지 않는다.

### 3.4 규칙·프롬프트·기준 데이터가 추가된 작업

적용 조건:

- 실행에 사용되는 규칙, 프롬프트 또는 기준 데이터가 승인된 자산으로 등록됨

추가 검토 내용:

- 자산 ID와 버전
- 출처·기준일·체크섬
- 입력 변수와 적용 범위
- 검토되지 않은 자산의 실행 차단
- 실행 결과에서 사용한 자산을 역추적할 수 있는지 확인

실제 자산의 위치와 형식은 해당 담당자가 확정한 뒤 추가한다. 하네스 담당자는 메타데이터·무결성·추적 검사를 연결한다.

### 3.5 실제 AI 파이프라인이 추가된 작업

적용 조건:

- 파싱·검색·판정·수정안 등 실제 AI 처리 기능이 구현됨
- 각 기능의 실패 조건과 검증 기준이 확정됨

추가 검토 내용:

- 원문 위치가 입력부터 결과까지 보존되는지
- 근거가 없거나 검증에 실패한 결과를 확정 판정으로 노출하지 않는지
- 선행 검사가 실패하면 후속 검사를 성공으로 표시하지 않는지
- 판단보류와 부분 실패가 결과에 구분되는지
- 제품 AI 기능이 확정된 경우에만 해당 기능별 불변식을 추가하는지

RMA·CBR 등 특정 기능의 책임은 관련 아키텍처와 구현이 확정된 뒤 별도 결정으로 추가한다. 현재 하네스 문서만으로 해당 기능이나 경로를 확정하지 않는다.

### 3.6 평가셋이 준비된 작업

적용 조건:

- 검수된 평가 인스턴스와 비교 기준이 준비됨
- 동일 조건으로 재실행할 수 있는 명령과 결과 형식이 정의됨

추가 검토 내용:

- 데이터셋 무결성
- split 간 중복·누수
- 기준선과 변경안의 동일 조건 비교
- 실제 실행하지 않은 지표의 결과 포함 방지
- 품질·판단보류·근거·시간·비용 지표의 추적

평가 자산과 실행 결과의 실제 경로는 평가 범위와 형식이 확정된 뒤 추가한다.

### 3.7 서버 계약과 웹 동기화가 필요한 작업

적용 조건:

- 서버 계약을 공식 원천으로 삼고 버전·SHA 추적 방식이 합의됨

추가 검토 내용:

- 서버 계약 산출물의 버전과 Git SHA 기록
- 웹 소비자 검증 연결
- 호환되지 않는 계약 변경의 CI 실패
- 동기화 과정에서 화면 구현을 자동 수정하지 않는지 확인

서버·웹 동기화 스크립트와 `contracts.lock`은 이 조건이 충족된 뒤 추가한다.

### 3.8 운영 환경이 추가된 작업

적용 조건:

- 실제 사용자 문서, 외부 API, 모델 키 또는 배포 환경을 사용함

추가 검토 내용:

- 로그·Trace·CI 아티팩트의 원문·개인정보·토큰 비노출
- 외부 API 시간 초과·재시도·최종 실패 상태
- 리포트 보존·삭제와 장애 복구
- 운영 환경별 최소 권한과 비밀정보 관리

운영 검사와 runbook은 실제 운영 방식이 확정된 뒤 추가한다.

## 4. 공통 작업 순서

작업 내용에 해당하는 항목을 선택한 뒤 다음 순서로 진행한다.

```text
변경 근거와 이슈 확인
→ 파일 작성 주체와 리뷰어 결정
→ 실제 자산 또는 실행 명령 작성
→ 영역 담당자의 검사·실패 사례 작성
→ 하네스 검사 코드·정책·자체 테스트 리뷰
→ 로컬 검사
→ CI 연결
→ 관련 문서 갱신
→ PR에 실행 결과·미수행 검사·남은 위험 기록
```

필수 확인 명령:

```bash
./scripts/run-harness.sh check
./scripts/test-harness.sh
```

웹 변경이 함께 포함되면 웹 레포의 공식 검사 명령도 실행한다.

## 5. 새 검사 완료 조건

새 검사는 다음 조건을 모두 만족해야 한다.

- `HAR-*` 검사 ID가 있다.
- 검사 대상과 적용 조건이 명확하다.
- 정상 사례가 통과한다.
- 실패 사례가 예상 ID와 메시지로 실패한다.
- 대상이 없을 때 `not_applicable`인지 실패인지 기준이 정의되어 있다.
- 로컬과 CI가 같은 명령을 실행한다.
- 리포트에 검사 상태와 발견 사항이 남는다.
- 정책·코드·테스트·문서의 경로가 실제 구조와 일치한다.
- 하네스가 제품 코드나 계약 의미를 임의로 변경하지 않는다.

## 6. 현재 생성하지 않는 파일

다음 파일은 관련 구현과 합의가 생기기 전에는 빈 형태로 만들지 않는다.

- 실제 API·AI 계약 Schema와 예시
- 규칙 카탈로그와 프롬프트 본문
- 정답셋·기준선·평가 결과
- 백엔드·AI 프로젝트 설정과 Dockerfile
- 서버 계약 내보내기와 웹 동기화 스크립트
- 계약 snapshot과 `contracts.lock`
- 배포·DB·큐·클라우드별 검사
- 운영 복구 문서와 리포트 Schema

이 파일들은 실제 자산·실행 명령·담당 범위가 확정된 작업에서 해당 검사와 함께 추가한다.
